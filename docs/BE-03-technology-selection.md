# BE-03: Technology Selection

**Проект:** Intelligent Kanban System с AI-ассистентом для автоматического создания задач из голосовых сообщений
**Задача:** BE-03 — выбор и обоснование технологий
**Статус:** Draft v2 (решение: локальный запуск AI)
**Дата:** 19.10.2026

---

## 1. Цель

Выбрать и обосновать технологии для системы, которая принимает голосовое сообщение, распознаёт речь, извлекает из текста структурированную задачу (название, описание, исполнитель, срок, приоритет) и создаёт карточку на канбан-доске.

## 2. Требования, влияющие на выбор

| ID | Требование | Комментарий |
|----|-----------|-------------|
| R1 | Поддержка языков: **казахский, русский, английский** | Минимальное требование супервайзера |
| R2 | Устойчивость к смешанной речи (kk↔ru, ru↔en) | Типичная ситуация для пользователей в Казахстане |
| R3 | **AI запускается локально** | Решение проекта: голосовые и тексты задач не покидают сервер |
| R4 | Нулевая стоимость использования | Учебный (дипломный) проект; только open-source модели |
| R5 | Простота интеграции с Python | Backend на Python |
| R6 | Структурированный и валидируемый результат | Задача сохраняется в БД без ручного разбора текста |
| R7 | Модель STT выбирается командой | Готового STT-сервиса нет, разрешено использовать любую модель |

### 2.1 Выбор языков

Система поддерживает **kk, ru, en** на всех уровнях:

- **Распознавание речи:** язык определяется автоматически, пользователь может указать его вручную (это повышает точность для казахского).
- **Извлечение задач:** LLM получает текст на любом из трёх языков. Поля задачи сохраняются на языке оригинала, служебные поля (priority, status, deadline) хранятся в нормализованном виде (enum, ISO-дата).
- **Интерфейс:** локализация kk/ru/en.

Казахский — самый сложный из трёх языков: это малоресурсный язык, и базовые мультиязычные модели распознают его заметно хуже, чем русский и английский. Поэтому для казахского используется отдельная дообученная модель.

### 2.2 Где запускать AI: облако или локально

**Решение: локально (self-hosted), все модели open-source.**

| Критерий | Облачное API | **Локально** |
|---|---|---|
| Приватность | Данные уходят провайдеру | **Данные не покидают сервер** |
| Стоимость | Оплата за минуту / токены | **Бесплатно** (только своё железо) |
| Зависимость от интернета и лимитов | Есть | **Нет** |
| Контроль над моделью (дообучение, замена) | Нет | **Полный** |
| Качество на казахском | Высокое у лучших сервисов | Достаточное при использовании дообученных моделей |
| Требования к железу | Нет | GPU желательна; на CPU работает медленнее |
| Сложность развёртывания | Низкая | Средняя (решается Docker + Ollama) |

**Обоснование:** локальный запуск даёт полную приватность голосовых данных, нулевую стоимость и независимость от внешних сервисов. Слабое место — казахский язык у базовых моделей — закрывается open-source моделями, дообученными на казахском корпусе KSC2 (ISSAI, Nazarbayev University).

## 3. Сравнение Speech-to-Text (локальные модели)

### 3.1 Кандидаты

| Критерий | Whisper large-v3 / large-v3-turbo (базовый) | **Whisper, дообученный на казахском** (KSC2) | Soyle (ISSAI) | Vosk |
|---|---|---|---|---|
| Казахский | Слабо: путает с турецким, галлюцинирует; в исследовании WER ~77% | **Хорошо: WER ~15–18%** на тестовой части KSC2 | Лучший результат в исследовании (WER 18,6% на доменных данных) | Есть модель, качество ниже Whisper |
| Русский / английский | **Отлично / отлично** | Хуже базового (модель заточена под kk) | Поддерживаются | Есть модели |
| Смешанная речь | Автоопределение языка | Частично (kk + немного ru в обучении) | Частично | Нет |
| Размер / железо | large-v3 ~1,5B; turbo быстрее; на CPU через faster-whisper (int8) | Аналогично базовому Whisper (base → large) | Whisper-подобная, ONNX | Очень лёгкая, CPU |
| Интеграция с Python | `faster-whisper`, `transformers` | `transformers` (Hugging Face) | `optimum` + ONNX Runtime | `vosk` |
| Лицензия | MIT | Открытые веса (Hugging Face) | Открытые веса | Apache 2.0 |

### 3.2 Решение: маршрутизация по языку

Ни одна модель не лучше всех на всех трёх языках, поэтому используется связка из двух моделей:

1. **Определение языка** — базовый Whisper (`faster-whisper`, large-v3-turbo) по первым секундам аудио.
2. **ru / en** → распознаёт тот же базовый **Whisper large-v3-turbo** (быстрый, отличное качество).
3. **kk** → распознаёт **Whisper, дообученный на казахском** (кандидаты: `whisper-large-v3-tulpar`, `whisper-turbo-ksc2`, `whisper-base.kk` для слабого железа).
4. **Смешанная речь** — по умолчанию казахская модель; пользователь может переключить язык вручную.

Окончательная казахская модель выбирается по результатам собственного бенчмарка (раздел 7): сравниваются 2–3 дообученные модели и базовый Whisper.

**Почему не Soyle и Vosk:** Soyle — сильный кандидат и остаётся в списке для бенчмарка, но сложнее в интеграции (ONNX-пайплайн). Vosk лёгкий, но заметно уступает Whisper по качеству.

## 4. Сравнение подходов к извлечению задач (NLP)

### 4.1 Подходы

| Критерий | Правила + regex + NER (spaCy) | Дообученная модель (BERT / T5) | **Локальная LLM + JSON Schema** |
|---|---|---|---|
| Поддержка kk/ru/en | Плохо: для казахского нет готовых пайплайнов | Нужен размеченный датасет на 3 языках | Хорошо «из коробки» |
| Понимание контекста («до пятницы», «пусть Айгерим сделает») | Слабо | Средне | Хорошо |
| Нужны обучающие данные | Нет, но много ручных правил | Да, сотни–тысячи примеров | Нет (промпт + схема) |
| Гарантия формата ответа | Да | Да | Да (structured outputs в Ollama) |
| Железо | CPU | CPU/GPU | GPU желательна (модель 7–8B в 4-бит ~5–6 ГБ) |
| Время разработки | Высокое | Очень высокое | Низкое |

### 4.2 Решение

**Локальная LLM через Ollama со строгой JSON-схемой.** Ollama поддерживает structured outputs: в запросе передаётся JSON-схема, и модель обязана вернуть ответ в этом формате.

| Модель | Плюсы | Минусы |
|---|---|---|
| **Qwen (7–8B)** | Сильная мультиязычность, хорошо следует JSON-схеме | Казахский слабее, чем ru/en |
| **ISSAI KazLLM 1.0 8B** (на базе Llama 3.1) | Специально обучена на казахском | Нужно проверить качество структурированного вывода |
| Llama 3.1 8B | Широкая поддержка, много квантований | Казахский слабее |

Основная модель выбирается по результатам теста извлечения (раздел 7): Qwen и KazLLM прогоняются на одних и тех же расшифровках. Для слабого железа есть запасной вариант — модель 3–4B.

Схема задачи описывается один раз как Pydantic-модель и используется для ответа LLM, валидации и API:

```python
class Priority(str, Enum):
    low = "low"; medium = "medium"; high = "high"

class ExtractedTask(BaseModel):
    title: str                      # краткое название, язык оригинала
    description: str | None
    assignee_name: str | None       # имя из речи, сопоставляется с пользователями
    deadline: date | None           # ISO 8601, относительные даты разрешаются от даты сообщения
    priority: Priority = Priority.medium
    language: Literal["kk", "ru", "en"]

class ExtractionResult(BaseModel):
    tasks: list[ExtractedTask]      # одно сообщение может содержать несколько задач

# вызов: ollama.chat(model=..., messages=..., format=ExtractionResult.model_json_schema())
```

**Защита от ошибок LLM:**
- результат всегда проходит Pydantic-валидацию;
- задача создаётся как **черновик** и попадает на доску только после подтверждения пользователем;
- исходная транскрипция и сырой ответ LLM сохраняются для отладки и оценки качества.

## 5. Backend, база данных, API

### 5.1 Backend-фреймворк

| Критерий | **FastAPI** | Django + DRF | Flask |
|---|---|---|---|
| Асинхронность (долгие вызовы STT/LLM) | Нативная | Частичная | Через расширения |
| Валидация данных | Pydantic (та же схема, что для LLM) | Serializers | Вручную / Marshmallow |
| Автодокументация API | OpenAPI/Swagger из коробки | Через дополнения | Через дополнения |
| WebSocket | Встроено | Django Channels | Через расширения |
| Загрузка файлов (аудио) | `UploadFile`, просто | Да | Да |
| Порог входа | Низкий | Средний | Низкий, но всё собирать самому |

**Решение: FastAPI.** Async-модель подходит для ожидания долгих операций распознавания и генерации, а Pydantic даёт единую схему от ответа LLM до REST-ответа. Swagger-документация генерируется автоматически.

### 5.2 База данных

| Критерий | **PostgreSQL** | MongoDB | SQLite |
|---|---|---|---|
| Модель данных канбана (доска → колонка → задача → пользователь) | Реляционная, с внешними ключами | Документная, связи вручную | Реляционная |
| Хранение сырых ответов AI | JSONB | Нативно | JSON (ограниченно) |
| Транзакции (перемещение карточек, порядок) | Полные ACID | Есть, но сложнее | Да, но слабая конкурентность |
| Готовность к продакшену | Да | Да | Нет (только dev/тесты) |

**Решение: PostgreSQL** + SQLAlchemy 2.0 (async) + Alembic для миграций. SQLite — только в unit-тестах.

### 5.3 API

- **REST (FastAPI):** CRUD для досок, колонок, задач, пользователей; `POST /voice-messages` для загрузки аудио.
- **WebSocket:** обновление доски в реальном времени.
- **Аутентификация:** JWT (OAuth2 password flow).
- **Фоновая обработка:** распознавание и LLM занимают секунды–десятки секунд, поэтому выполняются в фоне. MVP — FastAPI `BackgroundTasks`; далее — отдельный AI-воркер (Celery/ARQ + Redis), чтобы модели загружались в память один раз.

## 6. Итоговый стек

| Слой | Технология | Ключевая причина |
|---|---|---|
| Языки | Казахский, русский, английский | Требование проекта; автоопределение языка |
| Запуск AI | **Локально (self-hosted, open-source)** | Приватность, нулевая стоимость, независимость |
| Speech-to-Text (ru/en + определение языка) | **Whisper large-v3-turbo** через `faster-whisper` | Лучшее качество ru/en, быстрый инференс, работает на CPU и GPU |
| Speech-to-Text (kk) | **Whisper, дообученный на KSC2** (итоговая модель — по бенчмарку) | WER ~15–18% на казахском против ~77% у базового |
| Извлечение задач | **Ollama + Qwen / KazLLM 8B + JSON Schema** | Мультиязычность без обучения, гарантированный формат |
| Backend | **Python 3.12 + FastAPI** | Async, Pydantic, OpenAPI |
| ORM / миграции | SQLAlchemy 2.0 + Alembic | Стандарт для FastAPI |
| База данных | **PostgreSQL 16** | Реляционная модель + JSONB |
| API | REST + WebSocket, JWT | CRUD + real-time доска |
| Фоновые задачи | BackgroundTasks → AI-воркер (Celery/ARQ + Redis) | Не блокировать API; модели в памяти один раз |
| Хранение аудио | Локальный volume | Аудио удаляется после обработки |
| Инфраструктура | Docker Compose (api, db, ollama, worker) | Запуск всего стека одной командой |
| Тестирование | pytest, httpx, jiwer | Unit- и API-тесты, бенчмарк STT |
| Процесс | GitHub/GitLab + Kanban-доска | Цифровой след разработки |

### 6.1 Требования к железу

| Конфигурация | Что запускается | Ожидаемая скорость |
|---|---|---|
| GPU 8+ ГБ VRAM | Whisper large-v3-turbo + kk large-модель + LLM 7–8B (4-бит) | Секунды на сообщение |
| Только CPU, 16 ГБ RAM | faster-whisper (int8), kk base/small-модель, LLM 3–4B | Десятки секунд на сообщение — приемлемо для фоновой обработки |

### 6.2 Пайплайн обработки голосового сообщения

```
Аудио (kk/ru/en)
   │  POST /voice-messages
   ▼
FastAPI ── сохраняет файл, статус "processing"
   │  background task / AI-воркер
   ▼
Whisper large-v3-turbo: определение языка
   ├── ru / en ──► Whisper large-v3-turbo
   └── kk/mixed ─► Whisper (fine-tuned KSC2)
   │  транскрипция + язык
   ▼
Ollama LLM (JSON Schema) → ExtractionResult
   ▼
Pydantic-валидация → черновики задач в PostgreSQL
   │  WebSocket-уведомление
   ▼
Пользователь подтверждает / редактирует → карточка на доске
```

STT и LLM подключены через интерфейсы (`SpeechToTextProvider`, `TaskExtractor`), поэтому модель меняется конфигурацией, без изменения бизнес-логики.

## 7. План проверки выбора (тестирование)

1. **Тестовый набор:** 15–20 записей по 10–40 секунд: 5 kk, 5 ru, 5 en, 3–5 смешанных (kk+ru). Содержание — реалистичные рабочие поручения («Айгерим, подготовь отчёт к пятнице, это срочно»).
2. **Эталон:** ручная расшифровка каждой записи (`.txt` рядом с аудио).
3. **Метрики STT:** WER и CER по каждому языку и модели; время обработки; используемое железо.
4. **Метрики извлечения:** доля правильно заполненных полей (title, assignee, deadline, priority) для Qwen и KazLLM.
5. **Результаты** сохраняются в репозиторий (`benchmarks/results/*.csv`) и сводятся в таблицу (раздел 8).

Скрипт: `benchmarks/stt_benchmark.py`.

## 9. Риски

| Риск | Митигация |
|---|---|
| Нет GPU, медленная обработка | Фоновая обработка, int8-квантование, модели меньшего размера (base/small, LLM 3–4B) |
| Низкая точность на смешанной kk/ru речи | Ручной выбор языка в UI; редактирование черновика перед созданием задачи |
| Ошибка определения языка (kk ↔ tr) | Ограничить выбор языков тремя (kk/ru/en); подсказка языка от пользователя |
| Галлюцинации LLM (выдуманные исполнители/сроки) | Строгая схема, nullable-поля, подтверждение пользователем |
| Объём моделей (несколько ГБ) | Загрузка один раз в Docker volume; модели не хранятся в git |
