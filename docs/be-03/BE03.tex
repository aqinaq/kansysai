\section{Goal}

Select and justify the technologies for a \textbf{commercial Kanban product} used by company employees, project managers, teachers and students. The AI assistant is built into the workflow: the user speaks or types a command, the system understands it, shows the proposed action and performs it on the board after confirmation.

\subsection{AI Pipeline}

\begin{center}
\small
Voice Input $\rightarrow$ Speech-to-Text $\rightarrow$ Intent Recognition $\rightarrow$ Entity Extraction $\rightarrow$\\
Validation \& Resolution $\rightarrow$ User Confirmation $\rightarrow$ Backend Action $\rightarrow$ Kanban Update
\end{center}

{\tblstart
\begin{xltabular}{\textwidth}{P{3.4cm} P{2.6cm} L}
\toprule
\textbf{Step} & \textbf{Where} & \textbf{Technology} \\
\midrule
\endhead
Voice Input & Browser & MediaRecorder API (WebM/Opus), uploaded to MinIO via the backend \\
Speech-to-Text & AI worker & Whisper large-v3-turbo + Whisper fine-tuned on Kazakh (Section~\ref{sec:stt}) \\
Intent Recognition + Entity Extraction & AI worker & LLM with tool calling: one call returns a list of actions with parameters (Section~\ref{sec:llm}) \\
Validation \& Resolution & Backend, no LLM & Pydantic schemas, assignee lookup among project members, task search (pg\_trgm), date and permission checks \\
User Confirmation & Frontend & Preview cards with missing and ambiguous fields highlighted; transcript and fields can be edited \\
Backend Action & Backend & The same domain services as manual UI actions (shared permission checks and audit) \\
Kanban Update & Frontend & WebSocket event; the board updates for all members \\
\bottomrule
\end{xltabular}}

\textbf{Key principle.} The LLM only \emph{understands the command and proposes} an action. Everything that changes data is ordinary backend code that runs after the user confirms, with the same permission checks as manual actions. As a result, the AI cannot change someone else's task or create a task without confirmation.

\subsection{Decision: Self-Hosted STT with Language Routing and a Cloud Fallback}

\begin{enumerate}
  \item \textbf{Automatic language detection.} Whisper large-v3-turbo (\code{faster-whisper}) computes language probabilities, which are restricted to Kazakh, Russian and English and renormalised.
  \item \textbf{Routing without a hint.} The Kazakh model is used if Kazakh is the most likely language \emph{or} $p(\mathrm{kk}) \ge 0.30$. The threshold handles mixed speech: a Kazakh sentence with Russian and English terms is often detected as Russian, but with a noticeable Kazakh share. Otherwise, Russian and English speech is transcribed by Whisper large-v3-turbo with the detected language.
  \item \textbf{Language selected by the user.} If the user selects a language in the UI, detection is skipped: Kazakh goes to the Kazakh model, Russian and English to Whisper large-v3-turbo. For mixed speech, the UI suggests Kazakh.
  \item The user can \textbf{correct the transcript} before it is processed.
  \item \textbf{Fallback:} if the local STT is unavailable or overloaded, a cloud provider is used (enabled in the workspace settings).
\end{enumerate}

The 0.30 threshold is a starting value; it is a parameter tuned with the benchmark. The benchmark (\code{benchmarks/stt\_benchmark.py}) evaluates multilingual models separately in two modes: \textbf{auto} (automatic language detection, the main product scenario) and \textbf{hint} (language selected by the user). For auto mode it also reports language-detection accuracy and how mixed recordings are routed. The final Kazakh model is chosen from the benchmark results.

\textbf{Rationale.} Voice is the most sensitive data in the system. Self-hosted STT addresses privacy and keeps costs flat as the number of users grows, while the fine-tuned model compensates for Whisper's weakness in Kazakh. The cloud fallback improves reliability (R8).

\section{LLM for Command Understanding}\label{sec:llm}

\subsection{What the Model Must Do}

From a single utterance, often with recognition errors and mixed languages, the model must produce an \textbf{action plan} that strictly follows a schema. Example for the command \textit{«Создай задачу для Данияра: подготовить презентацию проекта до пятницы, высокий приоритет»} (“Create a task for Daniyar: prepare the project presentation by Friday, high priority”):

\begin{Verbatim}[fontsize=\small,frame=single,framesep=6pt,rulecolor=\color{gray!50}]
{
  "actions": [
    {
      "type": "create_task",
      "params": {
        "title": "Подготовить презентацию проекта",
        "assignee_mention": "Данияр",
        "deadline": "2026-10-23",
        "deadline_phrase": "до пятницы",
        "priority": "high"
      },
      "missing": [],
      "confidence": 0.92
    }
  ],
  "clarification_needed": null
}
\end{Verbatim}

Requirements: tool calling or JSON Schema, understanding of Kazakh, Russian and English, several assignments in one utterance, Kazakh case forms of names («Даниярға» $\rightarrow$ «Данияр»), and relative dates. Task titles are kept in the original language.

\subsection{Comparison}

\toprule
\textbf{Criterion} & \textbf{Rule-based NLU (regex + spaCy NER)} & \textbf{Local 7--8B LLM (Qwen 3 / ISSAI KazLLM via Ollama)} & \textbf{Cloud Flash/mini-class LLM (Gemini Flash, OpenAI mini)} \\

Cost & Development time only & Hardware only & Estimate: $\approx$1.5k input + 300 output tokens per command $\approx$ \textbf{\$0.005 per command} \\

Rule-based NLU was rejected because covering eight actions, three languages and mixed speech with hand-written rules is not realistic (R1, R2); it remains useful for small deterministic checks, such as recognising status and priority keywords.

\subsection{Decision: Hybrid Behind a Single \code{CommandParser} Interface}

\begin{itemize}
  \item \textbf{Default mode: a cloud Flash/mini-class LLM} with tool calling. For a real product, the deciding factors are reliable parsing of complex Kazakh commands, response time (the user is waiting for the card preview) and scaling without buying GPUs.
  \item \textbf{Private (on-premise) mode: a local LLM via Ollama} (Qwen 3 or KazLLM 8B). Enabled by configuration for organisations that cannot send text to external services; also used as a fallback when the cloud API is unavailable.
  \item Both providers implement the same interface and JSON schema. The specific model is chosen by testing on our 30+ scenarios: intent accuracy, field accuracy, rate of invented values and response time.
\end{itemize}

\textbf{Why the version 2 decision (fully local) was changed.} Without a powerful GPU, a local 7--8B model responds too slowly and parses several actions in one Kazakh utterance unreliably. This conflicts with the speed and AI-integration-quality criteria. Voice is still processed only on our server, and the local LLM mode remains available as an option.

\subsection{Protection Against Invented Data}

{\tblstart
\begin{xltabular}{\textwidth}{P{4cm} L}
\toprule
\textbf{Risk} & \textbf{Mechanism} \\
\midrule
\endhead
Invented assignee & The LLM returns only a mention (\code{assignee\_mention}). The backend looks it up among project members, normalising Kazakh case endings, handling transliteration and using fuzzy matching. If there is no match or several matches, the field is flagged and the user picks from a list \\
Invented deadline & The LLM returns both the date and the source phrase (\code{deadline\_phrase}). If the phrase is not in the transcript, the date is discarded. The backend checks that the date is not in the past, using the user's time zone \\
Wrong task when updating & The LLM returns a description of the task. The backend searches for candidates (pg\_trgm on titles in accessible projects): none means ``not found'', more than one means a clarification question \\
Invented tasks in answers (Search, Summary) & The backend runs the query on real data. The LLM only builds the filter (status, assignee, deadline); the answer contains real rows from the database \\
Action without confirmation & Changes are applied only via \code{POST /ai-commands/\{id\}/confirm} \\
\bottomrule
\end{xltabular}}
